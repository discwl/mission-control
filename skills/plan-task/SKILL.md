# Plan task

Follow **Agent-managed workspace labels** in `<kitRoot>/docs/agent-workflow.md`: the coordinator uses In Progress during active planning in a task-owned workspace, and Ready once the plan is approved and ready to execute. An open plan decision does not imply approval or a blocker. Preserve shared workspace and user-selected labels; verify and record any actual label change.

Start with `check-environment` and the exact task/run IDs. Read the task's acceptance criteria, relevant project rules, existing code patterns, and `workflowInstructions.effective.planning` from the verified context. Follow its source and clarification preferences without inventing access or requirements. Reuse answers and scope confirmation already given; when a requirement remains unresolved, record the question with `dev-flow.mjs ask`, ask it in chat and wait before implementing affected work. Write `plan.md` beside `task.md` with the intended behavior, smallest useful implementation steps, non-goals, affected files, validation commands, and open questions. Link a diagram only when it resolves a real design question.

At plan ready, review the workspace title against the clarified overall goal and each agent title against its assigned responsibility. This is the main checkpoint for refining vague generated names. Keep agent names to 2–5 purpose-specific words without the workspace prefix. Preserve user-chosen names; for any pre-existing title with unknown provenance, record a suggested change in `plan.md` instead of applying it. A designated coordinator may rename an explicitly managed, unlocked workspace using its exact host and workspace ID. Record any applied old/new title, resource ID, reason, and owner in the plan evidence. Follow the Naming checkpoints section of `<kitRoot>/docs/agent-workflow.md`.

Apply the project's plan decision policy. Unless the user already granted a decision for this scope in this conversation or the task record, request one in Mission Control: write `{ "kind":"plan", "question":"Approve this plan?", "summary":"<scope, steps, non-goals, checks in under 8000 chars>", "evidence":["<full path to plan.md>"], "plain":{ "built":"<what the user will get, in one or two sentences>", "recommendation":{ "action":"accept|fix|stop", "reason":"<one line>" } } }` to a temporary JSON file and run `node <kitRoot>\scripts\dev-flow.mjs request-decision --task <taskId> --run <runId> --server <serverId> --workspace <workspaceId> --cwd <workspace> --input <json-file>`. Write `plain` for a busy product owner who reads it in seconds: what they get and what you recommend, in everyday words, with no hashes, paths, IDs, file or tool names; keep those in `summary`. The CLI refuses IDs, commit hashes and file paths, and warns about file, code and tool names: reword those. Recommend `accept` unless you need the plan changed (`fix`) or the work should not go ahead (`stop`). `node <kitRoot>\scripts\dev-flow.mjs help` shows the input format. That records the plan stage as waiting. Then stop and report the decision ID; do not implement until Mission Control sends the decision. An already granted decision remains valid within its scope; material changes require a refreshed decision. A task status such as `ready` is not that decision.

When no decision is needed, record the stage through `node <kitRoot>\scripts\dev-flow.mjs record --task <taskId> --run <runId> --server <serverId> --workspace <workspaceId> --cwd <workspace> --input <json-file>`. The UTF-8 input is `{ "stage":"plan", "outcome":"completed|waiting|blocked", "summary":"...", "nextAction":"...", "evidence":["plan.md revision or path", "decision ID if any"] }`. Write the JSON to a temporary file, invoke the CLI, then remove only that temporary file. State the plan and decision state before implementation.
