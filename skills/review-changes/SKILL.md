# Review changes

Read **Agent-managed workspace labels** in `<kitRoot>/docs/agent-workflow.md`. This Reviewer remains read-only and reports the appropriate checkpoint to the coordinator; it does not mutate labels. The coordinator uses Review for a task-owned workspace while independent review or its decision is pending, and In Progress when approved fixes resume. Neither a clean verdict nor review approval proves delivery/Done. Shared workspace status must consider all linked work.

Run in a fresh Reviewer session with the exact task/run ID, acceptance criteria, plan, validation evidence, intended base, and candidate Git state. Do not edit application source, stage, commit, push, or create a PR. Read the kit's `docs/ocr-kit/reviewer-prompt.md` for the detailed review and coverage contract.

Use the installed `open-code-review-delegate` skill and OCR `delegate preview`/`delegate rule`; the host agent performs the reasoning. Use Gortex for focused code relationships. Select the actual candidate: a committed range when it covers the whole task, or explicitly requested workspace mode when relevant changes are uncommitted or the branch has no commit. Record excluded files and any review gaps. If OCR or required repository context is unavailable, return a blocker rather than a clean verdict.

Assess acceptance criteria separately from code defects. Tie findings and verdict to the examined revision/working-tree state. Return a review artifact and exact remaining actions to the task coordinator. Give each actionable finding a short title, severity (`high`, `medium`, `low`), detail, and file. The coordinator then asks the user in Mission Control with `dev-flow.mjs request-decision` and input `{ "kind":"review", "question":"...", "summary":"<verdict and coverage>", "evidence":["<review artifact path>"], "plain":{ "built":"<what the user gets>", "found":"<what the review found>", "recommendation":{ "action":"accept|fix|stop", "reason":"<one line>" } }, "findings":[{ "title":"...", "severity":"high", "detail":"...", "file":"...", "plain":{ "description":"<the problem in everyday words>", "impact":"<what happens if it is skipped>", "recommend":"fix|skip" } }] }`, and stops until the decision arrives. The coordinator writes every `plain` field for a busy product owner who decides in seconds: say what the user gets, what's wrong in everyday terms and what you recommend, with no hashes, paths, IDs, file or tool names (the CLI refuses IDs, commit hashes and file paths, and warns about file, code and tool names: reword those); the technical detail stays in `summary`, `title`, `detail` and `file`. Recommend `fix` when any finding should be fixed first (mark those findings `fix` and the rest `skip`), `accept` when every finding can be skipped, and `stop` when the work should not continue. `dev-flow.mjs help` shows the input format. A clean review still requests a decision with no findings. When verifying earlier findings, the reviewer reports which were fixed; the coordinator marks each with `dev-flow.mjs finding --finding <id> --status resolved --evidence "<review artifact and what was checked>"`, or back to `submitted` if the fix failed. it obtains fresh validation and review after material fixes. Limit the initial repair loop to two rounds, then escalate unresolved findings.
