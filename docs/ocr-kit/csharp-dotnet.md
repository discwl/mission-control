# C# and .NET correctness review

Version: 2026-09-16. Applies to C#, ASP.NET Core, EF Core and their directly related contracts and project configuration. Apply only the checks relevant to the changed behavior and the repository's actual framework, language, package and database-provider versions.

## Review contract: precision before volume

Report actionable defects introduced or exposed by this change. A finding needs a changed location, a reachable trigger, a concrete adverse outcome and evidence that the surrounding code does not already prevent it. Explain those facts briefly. Prefer no findings over speculative advice. Do not invent a numerical confidence score. Emit findings only when confidence is high; put consequential unresolved questions in the review's limitations, not its defect list.

Read the complete changed behavior before judging a line. Establish relevant target frameworks, nullable settings, hosting model, EF provider/version, serialization options and accepted requirements. Do not infer runtime behavior from a newer framework's defaults. For multi-targeted projects, identify the affected target. For project files, check consequential target, package, conditional compilation, resource or publish changes; do not apply C# syntax rules to XML.

Do not duplicate formatter, compiler, nullable-analyzer or established analyzer diagnostics unless they expose a material issue absent from the supplied validation evidence. Do not demand stylistic rewrites, XML comments, blanket architectural patterns, speculative micro-optimizations or tests unrelated to changed behavior. Existing defects outside the change are not new findings. Existing tests are evidence, not proof that every path is correct.

## Establish context and challenge every candidate

If Gortex is available, use focused symbol lookup and bounded smart context, then inspect relevant callers/callees, usages, implementations, inheritance/interfaces, dependency relationships and related tests. Resolve ambiguous symbols by namespace, containing type, signature and repository. Verify that graph responses describe the reviewed checkout/revision and relevant current source. A stale, degraded, partial or wrong-worktree graph cannot establish a defect or establish that a defect is absent.

Before claiming broken callers, interface incompatibility, missing implementations, unused code, unsafe concurrency, N+1 queries or broken contracts, check the affected definitions and actual consumers. Query indexed cross-repository consumers only when those repositories are available; identify their revisions and limits. Do not imply organization-wide coverage from one repository. Graph absence is not proof of absence: reflection, DI scanning, generated code, framework conventions, dynamic dispatch, routes, serialization and external consumers can escape static relationships. When necessary and permitted, use a small source slice or Git object to resolve the specific uncertainty. Do not bypass a denied tool by changing shells or disguising the same read. If verification remains blocked, disclose the gap and withhold the finding.

For every candidate, actively seek a counterexample to your claim: upstream validation, authorization policies, a lock, an existing transaction, ownership transfer, provider translation, a compensating action or a compatibility adapter. Cite the evidence that survives this check. Combine duplicate symptoms of one root cause. Anchor to a narrow changed range in the new revision; never fabricate a line number. Follow the host review's output schema and coverage ledger. Reviewing all selected files is coverage accounting, not a guarantee that every bug was found.

## Nullability, values, collections and exceptions

- Follow a possibly null value from its actual producer to the failing dereference or violated contract. Consider model binding, deserialization, database nulls, nullable-oblivious libraries, unconstrained generics and default values. A non-nullable annotation or null-forgiving operator is not a runtime guard; neither is its presence alone a bug. Respect prior checks, pattern matching, proven invariants and framework initialization.
- Detect incorrect default/empty handling, overflow or narrowing on reachable inputs, lost precision in money/quantities, and boundary or indexing errors. Name the relevant input. Do not demand checked arithmetic everywhere or replace every floating-point value with decimal.
- Verify deferred LINQ execution across disposal, mutation, exception and transaction boundaries. Report repeated enumeration only when it demonstrably repeats I/O, consumes a single-use source, changes results, repeats side effects or creates material work. A list enumerated twice is not automatically defective. Check whether an IQueryable still runs in the provider or has crossed into in-memory evaluation.
- Check escaping closures for actual captured mutable state and delayed execution. Distinguish a captured for-loop variable from modern foreach's per-iteration variable. Check deferred delegates for disposed scopes and unintentionally shared mutable references.
- Review equality/hash keys for mutations while stored in sets or dictionaries, unintended reference versus value equality, and record members whose collections or nested objects remain mutable. Records and with-expressions do not imply deep immutability; arrays/collections do not automatically gain sequence equality. Report only when the application relies on the incorrect assumption.
- Check that exception handling preserves the required failure signal, transaction outcome and cleanup. Identify swallowed failures that report success, retries that hide permanent failures, and cancellation treated as an unrelated server error. Do not require broad catches or logging at every layer. Rethrow/stack-trace advice needs a concrete diagnostic or behavioral consequence.
- Verify time semantics: instant versus local wall time, UTC conversion, DateTime.Kind, offset loss, daylight-saving transitions, expiry boundaries and database precision. DateTimeOffset preserves an offset, not a time-zone rule set. Use a monotonic elapsed-time source when clock adjustments can break a demonstrated duration requirement. Do not require DateTimeOffset for inherently date-only values.
- Check culture-sensitive parsing, formatting, casing and comparisons at persistence/protocol/security boundaries. Require an ordinal/invariant choice when a machine contract needs it; preserve intentional user-culture behavior. Check whether serialization changes names, enum values, omission of null/default values, converters, reference handling, number handling or timestamp formats.

## Asynchrony, cancellation and lifetime

- Find lost tasks where completion, failures or ordering are required: omitted awaits, async lambdas converted to Action, nested tasks, or parallel work returning success prematurely. async void is appropriate for required event signatures; otherwise prove its unobservable completion/error path matters. Do not report every deliberately discarded task: inspect its ownership, exception observation, shutdown behavior and delivery guarantee.
- For fire-and-forget work, verify that dependencies and data outlive the request, failures are observed, capacity is bounded where needed, and the required job survives process termination if durability is promised. Captured HttpContext or request-scoped DbContext used after the response is a concrete risk when that path can execute.
- Follow CancellationToken through cancellable I/O, EF operations, loops, delays and downstream calls when request/job cancellation must stop the work. Identify the missing propagation and its consequence. Respect intentional non-cancellable cleanup and completion after an irreversible side effect; blindly propagating an aborted request through a committed workflow can itself be wrong. Verify linked-token-source ownership and disposal.
- For .Result, Wait or GetAwaiter().GetResult, establish blocking on a relevant execution path. Do not automatically claim a classic synchronization-context deadlock in ASP.NET Core: its default request environment does not supply the old ASP.NET/UI context. Prove a captured context, custom scheduler, lock dependency or actual starvation/load risk. Do not prescribe ConfigureAwait(false) everywhere or Task.Run as a universal cure.
- Check ValueTask reuse/multiple consumption and premature pooled-resource reuse only where the API's actual contract makes them invalid. Await all concurrent operations before disposing their shared dependencies.
- Trace ownership of IDisposable/IAsyncDisposable, streams, readers, responses, connections, transactions, scopes and cancellation registrations. Detect leaks on exceptional/early-return paths and use after disposal, including a returned lazy sequence backed by a disposed resource. Respect DI-owned objects, transferred ownership and leaveOpen. Prefer await using where asynchronous cleanup is required by the real type and lifecycle, not merely because the interface exists.

## Concurrency and shared state

- Establish that the same mutable instance can be accessed concurrently before reporting a race. Inspect service lifetime, static state, timers, callbacks and worker parallelism; request-local state is not automatically shared. Describe an interleaving and its failed invariant.
- Check lock identity, consistent protection of all accesses, lock ordering, re-entrancy and awaits around asynchronous coordination. For SemaphoreSlim, pair successful acquisition and release across cancellation/errors; do not release when acquisition failed. Avoid assertions that every lock is a deadlock or every volatile field is thread-safe.
- Concurrent collections protect their documented operations, not multi-step business transactions or mutable values. Verify check-then-act sequences and GetOrAdd/AddOrUpdate factories that can execute more than once before reporting duplicated side effects. Lazy/task caches need actual failure, eviction, initialization or cancellation semantics checked. Atomics only fix the invariant they cover.
- Identify unbounded queues, uncontrolled fan-out, overlapping timer invocations and missing backpressure when input rate and resource limits make failure plausible and concrete. Preserve intentionally bounded, serialized or externally synchronized execution.

## ASP.NET Core and hosted services

- Trace the actual middleware/endpoint pipeline, including branches and short-circuits. Check ordering where it changes behavior: routing metadata, CORS, authentication, authorization, exception handling, response caching, forwarded headers and static files. Minimal hosting can add authentication/authorization middleware automatically; verify the target version and setup before reporting an omitted explicit call.
- Inspect DI registrations and construction paths. Detect a singleton retaining a scoped dependency or request data, a scoped dependency resolved from the root, and a disposed scope escaping into later work. Scoped services per background iteration via IServiceScopeFactory/IDbContextFactory can be correct. Constructor injection into conventional middleware differs from per-request Invoke injection and IMiddleware activation. Do not confuse transient lifetime with automatic thread safety or automatic disposal by the caller.
- Verify authentication scheme, issuer/audience/signature validation and endpoint authorization, including fallback/default policies, route-group conventions, filters, resource/tenant ownership and AllowAnonymous. A missing [Authorize] attribute alone is not evidence of public access. Authentication does not establish access to a particular object or tenant. Validate the actual bypass path and an untrusted request that reaches it.
- Check binding sources, validation and over-posting against the endpoint contract. Account for [ApiController], endpoint filters and configured validation; controllers and minimal APIs need not share defaults. Do not trust client-supplied identity/tenant/ownership fields. Check empty/missing/malformed values, body-size limits where relevant, route constraints, success/error response shapes and status codes consumers rely on. A preferred REST convention alone is not a finding.
- Check HttpClient/handler ownership, DNS refresh and response/stream lifetime on active paths. Both IHttpClientFactory and appropriately configured long-lived clients are valid. A typed client captured indefinitely by a singleton can defeat intended handler turnover; report only with the relevant configuration and impact. Verify cancellation and timeouts distinguish caller cancellation from dependency failure.
- In BackgroundService/IHostedService, verify startup/shutdown ordering, awaited execution, stopping-token use, scoped dependencies, bounded work and exception policy for the installed .NET version. Do not assume ExecuteAsync scheduling is identical across .NET releases. Check delivery/lease behavior across retries and restarts when the worker claims durability.
- Trace sensitive values into logs, traces, exception pages and HTTP responses. Identify the concrete exposed field and audience. Do not paste secrets or personal data into findings. Check logging templates when misuse loses essential diagnostics or exposes data; avoid generic logging-style comments.

## EF Core, SQL Server and PostgreSQL

- DbContext is not safe for simultaneous operations. Establish the shared instance and overlapping calls, including Task.WhenAll, lazy enumeration and concurrent background tasks. Separate contexts/scopes or factory-created instances may be correct. Pooling requires checking application/tenant state reset; pooled context state is not automatically equivalent to a fresh application object.
- Prove N+1 with a query-in-loop path or configured lazy-loading plus navigation access, realistic multiplicity and absent batching. A navigation property or missing Include alone proves neither a query nor N+1. Projection can fetch related data without Include. Check Include/split-query/cartesian growth, pagination ordering and data consistency against the provider/version and actual cardinality; do not prescribe split queries universally.
- Check tracking requirements before suggesting AsNoTracking: intended updates, identity resolution, relationship fixup and filtered Include behavior matter. Report dropped persistence when untracked entities are modified without attach/update, or stale/tracked state corrupts results. Do not demand no-tracking for every read.
- Inspect IQueryable composition, materialization and enumeration. Identify premature materialization that moves a substantial filter/join into memory, repeated query execution, unsupported translation and use after context disposal. EF Core does not silently client-evaluate every untranslatable expression; verify the exact operator, provider and version. Cite generated SQL/query logs or a clearly established execution path when needed.
- Check SaveChanges/SaveChangesAsync is reached and awaited for promised persistence, and that its affected-row/concurrency results are handled as required. A single SaveChanges generally has provider-supported transactional behavior; multiple saves, raw SQL and external messages are not automatically one transaction. Verify transaction scope, commit/rollback, execution-strategy retries, savepoints and cancellation around partial effects.
- Detect lost updates and inconsistent check-then-write business invariants using actual concurrency tokens, isolation, unique constraints and retry behavior. A missing rowversion is not automatically a bug. SQL Server rowversion and PostgreSQL concurrency mechanisms differ. A token conflict must not be silently treated as success; retries must reload/reconcile when required.
- Trace untrusted data into SQL text or identifiers. EF's interpolated parameterizing APIs differ from constructing a string before calling a raw API. FromSql/FromSqlInterpolated/ExecuteSqlInterpolated are not unsafe just because interpolation is visible. Raw variants can also be safe with parameters. Identifiers and SQL fragments need an explicit allowlist or equivalent validation; parameters cannot substitute for identifiers.
- Review migrations and model snapshots together, including data backfill, nullability, defaults, precision, indexes/constraints, renamed versus dropped objects and rolling-deployment compatibility. Do not blanket-exclude migrations as generated code. Flag destructive operations only with the data/rollout impact; an intentional reviewed removal is not automatically wrong. Never execute a migration against production during review.
- For performance, identify a substantial reachable defect: unbounded result/materialization, repeated round trips, demonstrably non-sargable hot queries, explosive joins or changed plans with evidence. Do not invent production row counts, missing indexes or provider behavior. Database collation, null semantics, timestamp mappings and pagination can differ between SQL Server and PostgreSQL; identify which supported deployment is affected.

## API contracts and distributed effects

- Compare changed routes, DTOs, required/optional fields, enum values, JSON names, defaults, status codes and error bodies with actual API consumers, OpenAPI/schema snapshots and contract tests. Check Angular/React callers and generated clients when present. C# nullability alone does not establish runtime JSON rejection or required presence; inspect serializer options, required members and constructor binding for the deployed version.
- Identify backwards incompatibility only against a real compatibility promise or supported consumer. Distinguish internal changes deployed atomically from public APIs or messages retained across deployments. If external consumers cannot be inspected, state the conditional compatibility risk and missing evidence without inventing broken callers.
- Check timeouts and retry policies together. Demonstrate duplicated non-idempotent effects, acknowledgement before durable completion, an unsafe idempotency-key scope, lost deduplication state or a DB/message partial failure. Verify outbox/inbox, transaction, uniqueness, broker redelivery and compensation already in place. Retrying every exception is not resilience; verify which failures are transient and whether cancellation/deadlines terminate the attempt sequence.
- Check cache invalidation, tenant-specific keys and stale read behavior only against a required invariant. Verify distributed locks/leases by expiration, ownership and fencing when correctness depends on exclusivity. A process-local lock cannot establish cross-instance exclusion, but not every deployment requires it.

## Security and final reporting

- For auth bypass, SQL injection, XSS, SSRF, path traversal, unsafe deserialization, command execution, insecure cryptography or dangerous file operations, trace an attacker-controlled source through existing validation to a reachable sink. State the violated trust boundary and concrete impact. Server-side template output, Razor encoding and React/Angular defaults differ from explicit unsafe HTML insertion; inspect the sink.
- For SSRF, consider redirects, DNS/IP resolution and cloud metadata/private endpoints where requests are attacker-directed. For paths, check canonical containment, platform separators/case, symlinks/reparse points and time-of-check/use where relevant. A string prefix or filename check is not always containment. Do not call every user-supplied URL or path exploitable without the necessary access path.
- Check deserialization type activation and permitted types, secret handling, token validation, key/nonce randomness/reuse and hard-coded credentials by actual use. Distinguish public identifiers and deliberate test fixtures from secrets. For browser cookie authentication, check CSRF at state-changing endpoints; CORS is not authorization. Bearer-only and non-browser flows have different threat models.
- Never broaden a review into exploitation, secret collection, production access or code modification. Report the smallest reproducible reasoning/test needed, the affected path, a narrow changed location, severity proportional to demonstrated impact, evidence and a concise remediation direction. Finish with explicit omissions and contextual limits, even when findings are empty.
