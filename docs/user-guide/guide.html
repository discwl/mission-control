What Mission Control does

Paseo runs coding agents (Claude Code, Codex, GitHub Copilot CLI and OpenCode) in workspaces on one or more computers. Mission Control adds the layer on top: it turns work into tasks, starts agents on them in their own worktrees, collects the questions agents need you to answer, and gets finished work reviewed and merged.

See everything

Every host, project, workspace and agent in one place, with search, filters and collapsible projects.

Run tasks

Write down what "done" means, then start an agent on it in its own branch and folder with one click.

Answer in one place

Plan approvals, review decisions and permission prompts from every agent, in the Attention tab.

Review and merge

Risk-sorted file-by-file review with comments, then a guarded Merge into your main checkout.

Keep tools in order

MCP servers, rules, skills and tool search for every provider, plus updates, branch naming and dependencies.

Start the day

The Morning check reads your Jira or Azure DevOps sprint and imports the items you pick as tasks.

Roadmap: toward an automated software factory

October 1, 2026 snapshot, with the Review improvements completed later in this session noted below. The detailed automation roadmap is optional local supporting material; this summary is embedded in the standalone guide.

The goal. Mission Control should automatically turn ready tasks into reviewed, deliverable work, with Paseo's native schedules keeping the process moving. You set priorities, answer genuine product questions and review results, without pressing Start for every task.

Current position: the manual workflow has many of the necessary parts. Reliable coordination between them is the main gap. Unattended operation is still planned. At the October 1 snapshot, the connected host had no saved agent profiles or schedules; this observation does not describe every host. This guide update enables no automation.

Tracker scope: each host uses either Jira or Azure DevOps tasks/work items. Planned intake will use that host's configured tracker, project and field/status mapping, preserving source links and task ownership.

When to start testing

Start manual testing now. Do not wait for sprint dates. The first automatic-start checkpoint is a ready task reaching user review with independent review evidence and recoverable state. It does not require scheduled tracker intake, a sprint dashboard or accurate estimates.

  1. Manual baseline — now. Use a small reversible task in a test project or isolated worktree. Record its task/run, actual revision and dirty state, commands, results and observed UI behavior.
  2. Scheduled dry run — after coordination exists. Report what would be imported, started, resumed, left waiting or escalated without dispatching work. Include duplicates, missing criteria, wrong context, dependencies and unavailable tools.
  3. Supervised pilot — before sprint features. One project, one active implementation task, three to five small tasks and manual delivery. Exercise overlapping checks, interruption, failed validation, review findings, unanswered decisions/permissions and offline hosts. New code after review requires fresh relevant verification.
  4. Unattended expansion — after the pilot passes. Observe several working days and set reliability thresholds from evidence. Limit new starts when the review queue grows, and verify pause and recovery controls.

Pilot settings still to choose: project/tasks, profiles, operating hours/timezone, cadence, concurrency, retry/repair limits, review-queue limit and delivery boundary. Morning intake plus daytime checks every 10–15 minutes, and two repair rounds before escalation, are proposals rather than active settings.

Profiles, schedules and independent review

  • Paseo schedules wake the coordinator. Progress stays in task/run records and receipts so a fresh coordinator can recover after downtime. It checks live state before acting and records its start, wait, retry or escalation reasons.
  • Paseo profiles configure the agents. Implementation and independent-review profiles need to be created, routed and applied at launch, including supported provider/model settings. A profile name alone does not establish reviewer independence or permission.
  • OCR supports the reviewer. OpenCode Review's ocr delegate preview selects scope and ocr delegate rule resolves rules; a fresh reviewer performs the review with Gortex context. The verdict must identify the revision and account for reviewed/excluded files. Missing required tools or context is a review gap, not a clean result.
  • Your review stays deliberate. A completed stage, idle agent or Done workspace label does not approve or deliver a task. Accepted work follows the project's authorized delivery route.

Host coordinators and a main-host supervisor

Recommended design · planned. Each host owns its tasks and agents. A supervisor on your main host watches progress across hosts and gathers the decisions and reviews that need you. This coordination layer still needs implementation and testing.

You: priorities & reviews→Main-host supervisor→Host coordinators→Task agents

Main-host supervisor

Combines host health, task progress, capacity and review queues. Requests checks or pauses through the owning host instead of launching competing workers.

One coordinator per host

A durable role that fresh agents can perform. Uses that host's Jira or Azure DevOps, repositories and profiles to claim eligible tasks, advance checks/review and record waiting or recovery reasons.

Task agents

Implement, validate and review within the exact task/workspace binding. An independent reviewer examines the candidate and evidence before work reaches your review queue.

  • One owner per task. Code enforces exclusive, time-bounded claims and rejects stale owners. Check the live agent before taking over an expired claim. Models provide judgment; code enforces transitions.
  • Records survive agents. Existing task/run records and action receipts retain the host, workspace, agent and candidate revision. Reconcile uncertain sends before retrying.
  • Capacity includes review. Start with one implementation per pilot project. Bound repairs/retries and limit new starts when reviews pile up or shared provider capacity is exhausted.
  • Disconnected is not failed. Main-host downtime must leave authorized remote work running. An unreachable remote host shows its last confirmed state; do not start replacement work elsewhere.
  • On track requires evidence. Show latest verified progress, stage, next action and waiting reason. Quiet agents are not automatically stuck; forecasts follow reliable timing history.

How schedules work together

Paseo schedules start fresh agents; heartbeats prompt an existing agent. Use schedules for routine coordination and bounded heartbeats for individual builds/investigations. Inventory existing jobs before adding any. These cadences are proposals, using configured operating hours and timezones.

Existing build/review schedules must join this policy rather than become competing task owners.

Use host-local profiles for coordinator, implementation and independent review responsibilities. Read their notes and apply the actual launch settings; profile names alone establish neither authority nor independence. See Paseo profiles.

Where Paseo Hub fits

Recommendation: use Hub where it saves dispatch and event infrastructure. Mission Control still owns readiness, task claims, evidence, decisions and delivery. The first local scheduled pilot should work independently of Hub.

Adoption and testing

Prove one local coordinator first, then add a second host and read-only main supervision before control requests. Evaluate Hub alongside that work: presence first, then one bounded coordinator trigger with recorded versions, host binding and execution IDs. Test overlapping schedules/events, lost responses, host/Hub downtime, recovery, pauses and fresh review. Each stage must have one dispatcher and produce no duplicate worker or unapproved delivery.

Testing need not wait for Hub or sprint dates. This roadmap update installs no service, creates no schedules and grants no execution permissions.

Timing, sprint ends and task deadlines

Record timing from the first pilot; forecast later. Track queue wait, first actual work to a review-ready candidate, review wait, and total cycle time from first work to verified delivery. Keep observed execution/check intervals and rework separate. Resuming must not reset the task's original start. Parallel agents' combined work time is not elapsed task time; missing data stays unknown.

Sprint end

The planning target for a group of tasks. A task without its own due date can use this as a derived target.

Task due date

An optional specific commitment. Distinguish a target from a hard deadline; do not copy the sprint end into every task's stored due date.

Forecast completion

A calculated range including checks, repairs and review wait. Show the supporting history and explain risks without moving commitments.

Update this roadmap after each testing stage with the date, candidate, passed/failed scenarios, evidence and next gate. The deployment limits and screenshot coverage still apply.

Key ideas

TermWhat it means
HostA computer running Paseo, such as pc-864 or a remote machine. Mission Control shows every host Paseo is connected to. Tasks, reviews and settings belong to the host Mission Control is installed on.
ProjectA repository Paseo knows, such as development-flow.
WorkspaceA working folder in a project, with its own agents and terminals. Each task's worktree is a workspace too.
AgentOne Claude Code, Codex, Copilot or OpenCode session working in a workspace.
TaskA piece of work with a title and acceptance criteria ("what will prove this is done?"). Tasks are plain files in the vault.
RunOne recorded attempt at a task, linked to a run agent. Its updates can record different authors, including reviewers. It records a stage (Intake, Plan, Build, Checks, Review, Fixes, Delivery, Handoff), an outcome, a next action and evidence.
Workspace labelA native Paseo tag attached to the whole workspace, such as In Progress or Review. It is not an agent's label, a task status, or proof of completion.
DecisionA question an agent asks you: approve its plan, or accept its review. Review decisions come with findings you can send back to be fixed.
WorktreeA separate folder and branch for task work, which helps isolate changes. Several agents can still contribute to one task or share a workspace, so they must coordinate their ownership.
VaultThe folder that holds task records, run evidence and daily reports: C:\dev-vault. It's Markdown, so Obsidian can open it too.

Getting around

Open Mission Control from Paseo's sidebar. The screen has two parts:

  • The host rail on the left: search hosts, switch between All hosts and Online, and pick a host. Each host card shows whether it's online, its workspace and task counts, and a badge for anything that needs you. Drag the cards to reorder them.
  • The main pane, with five tabs: Workspaces, Attention, Tasks, Review and Docs. Mission Control opens on Workspaces. Attention shows a count when something is waiting for you.

Tip. The small icon beside the title shows or hides Paseo's own sidebar, which gives Mission Control the whole window. On narrow screens and phones the panes stack instead of sitting side by side.

Rosters refresh every 20 seconds. If a host goes offline, its last known data stays visible and is marked as last observed.

Workspaces

The Workspaces tab lists every workspace on the selected host, grouped by project.

Search and filters

  • Search matches workspace and project names.
  • Show narrows the list: All workspaces, Running agent, Needs attention, Has tasks or Has active tasks.
  • Label filters by Paseo workspace label, and Project by project. Project only appears when the host has more than one project.
  • Clear filters resets everything. The count above the list (for example "9 of 9 workspaces") shows how much you're seeing.

The filters adapt to the space: one row on a wide window, Show on its own row with Label and Project side by side at medium widths, and stacked on narrow screens.

Projects and Git

Each project is a block you can fold with its arrow; Expand all and Collapse all do every project at once. The project header shows its workspace and task counts, its agents by state (running, idle, need you), the providers in use, and the last activity. Mission Control remembers which projects you folded.

Under each project header, the compact Git summary shows the default branch, a Pull latest refresh icon and an auto-fetch state icon. The branch override and auto-fetch switch are in Settings → Plugins → Mission Control → Project Git:

  • Default branch shows the branch new task worktrees start from, normally origin's default. In Project Git settings, select the project and use Change to choose an override.
  • Auto-fetch keeps origin's branches up to date in the background.
  • Pull latest fast-forwards the default branch to origin. It never merges or rewrites anything; if a fast-forward isn't possible, it tells you why.

A new task worktree always starts from the latest version of the default branch on origin. A project without a remote starts worktrees from its current branch instead, and the Git bar says so.

Renaming workspaces and agents

New workspaces and agents often get unhelpful names. Rename all (N) at the top of the tab opens Rename workspaces for the whole host; Review names on a workspace page does the same for that workspace's agents.

  1. Press Suggest on a row, or Suggest all. A small, fast model reads the current names, the linked task titles and each agent's first and latest prompts, and proposes a 2 to 5 word name.
  2. Edit any suggestion, and tick the rows you want. Names that are too long get a gentle warning.
  3. Press Apply selected. Nothing is renamed before this, and Undo puts the old names back.

The workspace page

Click a workspace to open its page. It combines the agent tree with a compact list of linked work; completed tasks no longer dominate the page.

  • Header: host and project, Paseo's status for the workspace, last activity, and labels. Open workspace jumps to it in Paseo; Tasks, Review changes and Documents open the matching tab for this workspace; Archive workspace archives it after a confirmation.
  • Agents: the workspace's agents as a tree, the same one as the Agents panel: each agent's provider and model, state and age, with sub-agents under their parents (see Sub-agents).
  • Terminals: appears only while the workspace has an active terminal.
  • Linked tasks: active assigned tasks appear first as compact, clickable title/status rows. Delivered and closed work is grouped under Completed tasks, collapsed by default. Open a row for its task, or use the header's Tasks shortcut to view and add work. Long internal IDs are no longer the main label.
  • Morning check: at the bottom; see Morning check.

Sub-agents

Agents can start two kinds of sub-agent, and Mission Control shows both with the agent that started them:

  • Separate agents: a full Paseo agent that another agent started. It has its own chat and appears in agent lists.
  • Helpers: short jobs that run inside an agent's turn, such as Claude Code's Agent tool (for example "Explore" or a fresh review). They have no chat of their own.

Agent cards on the workspace page, and task cards in the Tasks tab and the Mission panel, get a Sub-agents (N) row when there are any. Collapsed, it says how many there are and how many helpers are running ("2 helpers running"). Open it to see each sub-agent's name, what it was started for (a helper's description, or a separate agent's first prompt), its kind, status (running, finished, idle, error or stopped) and time. Separate agents have Open agent; a helper's Last messages shows its last few messages. Finished helpers stay a count until you open them.

Where a separate agent appears without its parent, for example because the parent works in another workspace or is archived, a line under its name says whose it is: Sub-agent of <parent> · <the parent's task> · <project / workspace>. Click it to open the parent. If the parent agent no longer exists, the line says so and isn't a link. In lists that include both, the sub-agent sits under its parent instead. The same line appears in the agent choice for sending review comments and in the Review names dialogs.

Helpers are read from this host's Paseo, so they appear only for the host running this Mission Control. On other hosts, or on a Paseo that can't list them, the row shows separate agents only.

In the agent tree (the Agents panel, the workspace page and the Mission panel), a sub-agent sits under its parent on a rail, and the parent's row counts its sub-agents and helpers. A separate agent's Started for line shows the prompt it was started with, and its task's number and title.

Looking never wakes a stopped agent. Paseo restarts a stopped agent to read its chat or list its helpers, so Mission Control asks only about live agents, checking each one's status with Paseo first. For a stopped agent, press Show what it was started for to read it on purpose.

Tasks

The Tasks tab shows the tasks of one workspace (pick it first, or use Change workspace). It opens on the Board; List gives a compact list instead, and Mission Control remembers your choice. Search with Find a task, and tick Active only to hide delivered and closed work. The narrow Tasks panel inside a workspace always starts on the list.

Creating a task

  1. Press + Task.
  2. Give it a short title, and write the acceptance criteria: what must be true when it's finished, and how you'll check it. Up to 4,000 characters.
  3. Press Add task. Mission Control creates the task's folder in the vault. Nothing starts yet.

Tasks can also come from Jira or Azure DevOps through the Morning check; those carry their ticket and an Open ticket link.

Due dates

Open a task and enter a Due date as YYYY-MM-DD, then press Save; Clear removes it. Cards show Due tomorrow, Due Oct 22 or Overdue, highlighted when the date is three days away or closer, and tasks with the earliest due date come first in each list and column. An agent started or resumed on the task is told the date and asked to say early if it can't finish in time. Due dates aren't imported from the tracker yet, and sprint forecasting is still planned.

Starting an agent

Open a task in the Tasks tab to manage its criteria, status and Agent workflow launcher. The compact Task details / View full details actions open its activity, decisions and artifacts; that reading view is separate from launching an agent.

  1. Keep Work in its own worktree ticked (the default for Git projects). The task gets its own branch and folder, and Review then shows only its work. The Branch line shows the exact name first; it follows your branch name templates.
  2. Choose the provider (claude, codex, copilot or opencode) and model.
  3. Choose the effort (how hard the model thinks) and the permissions. Bypass and Full Access skip permission prompts and are shown in amber as a reminder.
  4. Press Start task. The first message gives the agent the task, the project's profile, and the Development Flow skills it follows.

Slow starts. Creating a worktree can take a while. If it takes more than about 20 seconds, the panel shows "Starting the task…" and updates by itself when the agent is running.

Prefer typing? Use a chat command instead shows /mission-task <task ID>; Copy command and paste it into any agent's chat.

Following a run

  • Task status (inbox, ready, in progress, blocked, in review, delivered, closed) is the stored task record. The compact view makes it a badge; managing it is separate from recording an event or assigning a workspace label.
  • Latest update is the most recent run's recorded stage/outcome. Next action shows what was recorded next. Neither a later stage nor a completion check establishes approval, validation of today's revision or delivery.
  • Agents may include the linked run agent, other task-linked agents and recorded update authors. Use the named agent's action to choose a chat. Open run agent specifically opens the agent ID recorded on that run; it does not choose whichever agent is currently working. Open worktree opens the associated workspace.
  • When the agent is idle, Resume task sends it the latest task context. Continue launch finishes a start that was interrupted, without starting a second agent.
  • Open task documents shows the task's files in the Docs tab.

Activity, decisions and artifacts

The task header shows its title, a task-status badge, a separate Latest update, the recorded Next action and an update time. A task can be In review while its latest update says Handoff completed: the handoff happened, but the task still awaits review.

  • Activity: select a row such as Planning completed, Implementation completed or Handoff completed to reveal the recorded author, summary and evidence. The long report is collapsed by default. A checkbox means that event recorded completion; waiting and blocked use different indicators.
  • History limits: the detail view reads up to five updates from each of three recent runs. Older events can be omitted. Expand Run snapshots or Record issues when you need to inspect missing/conflicting records.
  • Decisions: inspect the task's open and recent plan/review decisions and their findings. An activity row named Review completed is not a substitute for this decision record.
  • Artifacts: select a readable document label to preview its Markdown. Headings, emphasis, lists and tables are rendered; metadata is hidden from the normal reading view. Raw source shows the original text; Technical details reveals the underlying path. Run records are grouped separately. Use Docs to edit eligible documents.
  • Evidence: expand its count to inspect references. A document not included in this bounded view is reported as not included; that is not proof that the file does not exist. Offline or failed refreshes are shown explicitly.
  • Agents: more than one agent can be associated with a task. Details try to resolve recorded agents beyond the loaded directory and keep a readable fallback when details are unavailable. A compact run shortcut can still show an agent if the loaded roster has no name; it represents that run's stored agent ID.

In the compact task list, expand the task row to read its Latest recorded update, then choose View full details for the complete reading view. Activity preview loads when expanded. Current live-agent state is distinct from recorded run state.

No invented progress. The guide and UI do not derive a success percentage, effort estimate or ETA from stage position. Progress-plugin row minutes are estimates; recorded elapsed time is a different fact.

Referencing a task in chat

Press the copy icon beside the task title in the detail-dialog header or task card/row. Attention

Everything waiting for you, in one list. The tab's count tells you how many things are waiting. Permission prompts come from every online host; decisions, questions, tasks to deliver and pull requests come from the host Mission Control is installed on. Show recent decisions lists the last ones you answered.

Every card under Needs you explains itself, so you rarely need to open the chat:

  • The task line names the task (number and title) and where the agent runs: host, project and workspace.
  • Where it's at says where things stand, in the agent's own summary. If the agent didn't write one, the card quotes its latest message, marked as a quote. Nothing is made up.
  • Needs from you says in one sentence what the agent is waiting for, with its recommendation when it gave one.
  • Conversation shows the agent's last few messages and steps, and Open agent is a small link for when you want the whole chat.

Looking never wakes an agent. Paseo restarts a stopped agent to read its chat, so Attention reads a chat by itself only while the agent is live. For a stopped or failed agent, it reads the chat only when you open Conversation.

Decisions and findings

Agents don't leave their questions buried in the chat. For a plan or a review they request a decision, and for anything else they record a question (see Waiting for you). There are two kinds of decision:

  • Plan decisions: approve the agent's plan before it builds, or send it back.
  • Review decisions: an independent reviewer checked the work; accept it, or send its findings back to be fixed.

Every card is written for you, not for engineers:

  • The first lines say what was built and what the review found, in everyday words.
  • Recommended gives the agent's advice with a one-line reason, and its button is highlighted.
  • The buttons say what they do. For reviews: Accept (it reads Accept, skipping N when open issues would be skipped), Fix N issues first and Stop. For plans: Approve plan, Change the plan and Stop.

More opens everything else:

  • Each open issue is described in plain words, with what happens if you skip it and its own Fix now / Skip choice. The choice starts on the agent's recommendation, and the buttons' labels follow your choices.
  • What each button does spells out the result of each answer before you press it.
  • A note for the agent is optional. Technical details holds the reviewer's full report, the evidence and the file references.

A note is never sent without you seeing it. If your answer needs one, for example because it skips issues or stops the task, the card first shows the exact action and note, and you can edit them. Your answer is saved first and sent to the agent when it's idle. If the agent is busy, the answer shows Saved, not sent with Send to agent.

Findings are verified. Approving is refused while earlier findings are still waiting to be verified. A fix only counts once a fresh review confirms it, so an agent can't mark its own work as fixed.

Waiting for you

Two kinds of card appear here, each with a Reply box that sends your answer straight to that agent on its host:

  • A question: a Mission Control task agent that stops to ask you something records it with a short "where it's at" and "what I need". The card leaves once the agent has your reply.
  • An error: an agent that Paseo reports as failed. The card says what failed, from Paseo's error message.

An agent that simply finished its turn doesn't get a card, because Paseo can't tell a question in the chat from a normal finish. Only recorded questions and errors are listed.

Permission prompts

When an agent needs permission for a tool, the prompt appears here with the task line, where the agent is (its latest message), and a Wants to line in plain words, for example the command it wants to run. The buttons are the agent's own choices (for example allow once, allow always, or deny), and Details shows the full command. Prompts also appear in the Mission panel of the agent's workspace.

Ready to deliver

A task whose review you approved, and which ran in its own worktree, appears under Ready to deliver. Until it's delivered, its changes live only on the task's own branch. How it's delivered depends on its project's Delivery setting: Merge into your main checkout for personal projects, or Open PR for work repositories.

Merge

Merge brings the task's changes into your main checkout:

  1. Commits the task's changes on its branch.
  2. Merges that branch into master, keeping a merge commit.
  3. Archives the task's workspace and deletes its branch.
  4. Marks the task delivered and tells its agent.

The commit message follows the repository's own conventions. When its paseo.json has commit message instructions (the same ones Paseo's Commit button uses, such as Conventional Commits), a small, fast model writes the message from the task's title, ticket and handoff summary. The confirmation shows it, and you can edit it before anything is committed. Without instructions, or if writing fails, the message is the task's title and ID.

Before anything happens, it checks that it's safe, and says exactly why if it isn't:

  • the files still match what you approved (a fingerprint is recorded when the review is requested);
  • the task's agent is idle;
  • your main checkout is clean, on the branch the worktree started from, with no merge or rebase in progress;
  • the merge wouldn't overwrite any local file, including ignored files such as .env;
  • the branch has something to merge.

When the merge is quick, the dialog then shows each step's outcome, including anything that was skipped. A merge that takes longer than about 20 seconds (for example with slow Git hooks, or while Paseo archives the worktree) carries on in the background:

If Git reports a conflict, Merge undoes it and leaves master as it was. It shows Merge needs you with the conflicting files; the task's work stays committed on its branch, ready for you (or the coordinator) to merge by hand. Merge never pushes, rewrites history or touches other branches.

After merging Mission Control itself, reload the plugin (Settings → Plugins → Reload) to see the changes.

Open PR

For a project that delivers by pull request, Open PR takes the place of Merge. It runs the same checks, except the ones about your main checkout, which it never touches. Its confirmation lists:

  • the commit of the task's work;
  • the push of the task's own branch, never forced and with no tags;
  • the draft pull request: which forge, the target branch, the title and the description.

The title and description follow the repository's paseo.json pull request instructions in the same way, and you can edit both in the confirmation. The ticket key stays in the title. If the repository has a pull request template, the model gets it too and keeps its sections. Only the task's title, ticket key, handoff summary, the instructions and that template are sent, never other files or secrets. Without instructions, the title comes from the Delivery title template and the description from the template plus the task's summary.

Mission Control then opens the PR itself, as a draft: with gh for GitHub, az for Azure DevOps (linking the work item), and Bitbucket Cloud's web API. It uses the sign-ins those tools already have, and never stores or shows a credential. The task moves to In review, and its PR link and number are saved on the task.

Pull requests and Clean up

Attention also lists the pull requests it opened, with their state: draft, open, merged or closed. Refresh or Check status reads the latest state from the forge.

  • When a PR is merged, it shows PR merged with Clean up. After a confirmation, this archives the task's workspace, deletes its local branch and marks the task delivered. Nothing is cleaned up without you.
  • Clean up refuses, and changes nothing, if the local branch has work the PR didn't include, or the worktree has uncommitted changes. Squash merges, branches deleted on the website, and review fixes pushed to the PR are all fine.
  • A PR closed without merging offers no cleanup.

Every Merge, Open PR and Clean up leaves a result card in Attention, with each step's outcome, until you press Dismiss.

  • You write the criteria, answer decisions, review the changes, and deliver: Merge for personal projects, and draft pull requests for work repositories.

Workspace labels and the agent workflow

A workspace label is a native Paseo tag for the whole workspace. Mission Control reads it for the workspace header and Label filter. It is separate from task status, the run's events and the agent-label metadata used for task/role associations.

You can manage labels through Paseo's native workspace label menu, or instruct the bound task coordinator to do it. The Development Flow kit now has workspace-label actions get, assign, remove and status. Assign can create a missing native label; remove detaches it without deleting the catalog's shared definition or changing its color.

A useful instruction. “For this task's verified host and workspace, inspect the native labels, apply the appropriate lifecycle label when safe, preserve unrelated labels, and record the verified result. If other tasks share the workspace, reconcile its overall status rather than using this task alone.”

The agent checks the exact daemon, workspace, project and real checkout, performs the permitted write, then reads the assignments back. An uncertain write is reported as unconfirmed: inspect the current labels before retrying. Agents never edit Paseo's private label stores, and assigning a label never changes the task record.

Task-bound read command for agents

Use the actual copied task ID and verified server/workspace IDs from the current task binding. The command below only reads; placeholders must be replaced.

node <kitRoot>/scripts/dev-flow.mjs workspace-label \
  --task <taskId> --server <serverId> --workspace <workspaceId> \
  --cwd <checkoutPath> --action get

The trailing backslashes above illustrate line continuation in a POSIX shell. In PowerShell, enter it on one line or use PowerShell continuation. Use --action assign --label "Review" or --action remove --label "Review" only for an explicitly intended label edit; the guarded lifecycle form is --action status --label "Review" --reason "<recorded reason>".

PausedYou explicitly paused the work. Agent inactivity is not an instruction to pause.
DoneRequired verification and authorized delivery/closure have actually finished; no other active linked task or agent still needs the workspace. A completed handoff or stage is insufficient.

Shared workspaces: one coordinator owns their overall label. The guarded status action refuses to replace it when another active task is linked; its Done check also verifies the complete live agent roster and the calling agent's identity. Preserve unrelated tags and user-selected labels. Explicit assignment/removal is available for an intentional coordinator/user choice; it is not an automatic override of shared-workspace state.

The nine skills now follow this policy from check-environment → intake-task → plan-task → execute-task → validate-changes → review-changes → fix-findings → prepare-delivery → write-handoff. Reviewers remain read-only and report a proposed label to the coordinator. Resume and handoff reconcile recorded versus live state and retain a concrete next action. Label failure is recorded separately from an implementation blocker.

Verified on the personal host with Paseo 0.10.2: temporary native label creation, assignment, removal and cleanup; 29 script tests and plugin typecheck passed. The adapter uses an exported internal client API with capability checks because the public plugin SDK/MCP agent-label interface is different. Future versions may need adapter updates. The nine installed Codex skill folders are links to the updated repository; already-running agents keep their loaded context until the instructions are read again.

Troubleshooting and where things live

SituationWhat to do
A change to Mission Control doesn't showReload the plugin: Settings → Plugins → Mission Control → Reload, or paseo plugin reload mission-control. paseo plugin logs mission-control should end with "Plugin ready".
A task is missing from the listIts task.md may be invalid (for example criteria over 4,000 characters). The list skips it and shows a warning naming the file.
Starting a task seems slowCreating a worktree can take a minute. The panel shows "Starting the task…" and updates by itself.
Merge refusesIts message says why: files changed since approval (request a fresh review), the agent is busy, or the main checkout has uncommitted changes. Fix that and press Check again.
Open PR says a tool is missing or not signed inSettings → Setup lists gh, az or Bitbucket credentials for the forges your projects use, with the exact install or sign-in command.
Clean up refusesIts message says why: the local branch has work the PR didn't include, or the worktree has uncommitted changes. Nothing was changed; push or discard that work first.
An answer says "Saved, not sent"The agent was busy. Press Send to agent once it's idle.
Activity says completed, but the task is In reviewThe recorded update and stored task status are separate. Inspect Decisions for approval and Artifacts for the report; a completion checkbox does not establish acceptance of the current revision.
An evidence document is not includedThe returned detail view is bounded. Inspect the exact task/run documents in Docs. Do not assume the file is missing until its actual target is checked.
A wiki link cannot openCheck its exact vault path, host and optional extension. Missing or ambiguous targets should give feedback; use the vault tree to select the exact record. Save/discard an unsaved note before leaving it.
A label write is unconfirmedAsk the bound agent to read workspace-label get before retrying. A timeout may occur after a write; do not blindly replay it or use a label as task approval.
The guarded status action refuses a shared workspaceAnother active linked task or agent prevents replacing the overall status. Have the workspace coordinator reconcile it; the individual task's state is not the whole workspace's state.

Where things live on each host:

  • C:\dev-vault: tasks, runs, decisions, reviews, handoffs and daily reports.
  • C:\dev-vault\Projects: one profile per project, including where the Development Flow kit is.
  • ~\.paseo\plugin-data\mission-control\config-backups: backups taken before any MCP setting changes.
  • Task worktrees: Paseo's worktree folder, one per task, removed when the task is merged and cleaned up.
